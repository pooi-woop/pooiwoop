从零搭一套轻量 CI/CD，并让它托管自己

本文由 AI 读取 D:\hym 各仓库的 git commit 记录自动生成（覆盖 2026-10-10 ~ 2026-10-13）

署名说明：e-commerce-frontend 里 Heyiming、xlagent 里 hym / Heyiming 均为本人提交；同事 wenhai03（why）的提交不并入本文统计。本文只讲我这两天从零搭起来的这套 xlagent-ci，以及它最后怎么把「自己」也接进了流水线。

0. 一句话概括

用零第三方依赖的一个 Node 脚本（server.mjs）做 Gitee WebHook 接收器，把「校验 → 构建 → 人工批准 → 部署」拆成可审计的阶段；一个 receiver 服务托管五个项目；最后让这套 CI 引擎托管它自己（自举），并用 Go-Zero 的蓝绿方案把后端发布做成了「一翻 nginx 标记就切流」。

两天里前后端一共落了几十个提交，主线其实是三件事：

  1. 把发版从”人肉 scp”收编成流水线——先在推送时把「环境变量/产物口径」这类低级错误卡死；
  2. 多项目化——一个 9090 服务，前端、两个后端仓库、再加上 CI 引擎自身、GPU 编排器，五条流水线各管各；
  3. 自举与治理——CI 管自己（自举部署最危险的坑就是”重启会杀掉正在部署的进程”），并把整套只读/批准能力收敛进平台管理页。

1. 缘起：一次「裸端口」事故

导火索很朴素：apps/pc/.env.local 里

构建产物里全站 URL 被拼成 http://...:9012/47.76.197.179:9012/api/...，大面积 404。这类「环境变量 / 产物口径」错误，在构建阶段完全能自动发现——只要有人把它写成一条门禁。

这就是第一次提交的动机（97a29bde）：

ci: 新增轻量 CI/CD（Gitee WebHook→校验/构建→人工批准部署）+ 修 env 裸端口

顺带把 .env.local 里 VITE_AGENT_API_BASE_URL、PUBLIC_BASE_URL、AGG_CHAT_URL 三处裸 host:port 补回 http:// 前缀。

为什么不用现成的 CI（Jenkins/GitLab CI/Drone）？

  • 目标机只有一台 14G 内存的云主机，还要和生产容器挤着跑；
  • 需求很窄：一个 push 钩子、串行构建、人工点一下部署，不需要 runner 集群 / 秘钥管理 / 缓存矩阵那一整套；
  • 自建 = 全部逻辑都在自己眼皮底下，每条门禁都能讲清楚为什么存在，出问题能当场改。

于是就有了 e-commerce-frontend/scripts/ci/ 这一个目录——它的全部内容就是这 12 个文件（外加服务端 config.json，含密钥、不入库）。

2. 整体设计：一条 push 的旅程

两条铁律：

  • CI 红了不能 CD；
  • CI 绿了也不会自动 CD——部署永远要人工发一次 POST /deploy/<proj>/<sha>。

第二条是刻意的：服务器上跑着真实生产，自动部署带来的收益远小于一次误触发的代价。所以这套系统的定位是「把错误挡在推送时，把部署变成一次有回滚锚的点击」。

5.1 两个不太显眼的修复

  • | tail 会吞掉退出码（73e92bed）：go vet ./... | tail -50 里，管道的退出码是 tail 的（恒 0），于是 vet 有错也判 success。改成先落文件再取 rc；
  • detached HEAD 判不出分支（c06c7148）：检出指定 commit 后 git rev-parse --abbrev-ref HEAD 恒返回 HEAD。改为优先用 webhook 的 ref（refs/heads/<branch>），缺失时用 git branch -r --contains <sha> 反查。

6.3 一个被推翻又修正的设计：怎么做到「色隔离」

两套色如果共用一套容器网络，platform:8001 这种裸服务名会解析到哪一色是歧义的。第一次尝试（26d8901e）想用「颜色专属容器名 Target」——给 pro2 的配置把上游目标改成 platform2:8001 之类。

后来发现更干净的解法（73e92bed）：每色挂各自的网络——

  • pro1 → xlagent 网络，pro2 → xlagent2 网络；
  • redis 同时接入两张网（别名 redis）；
  • 于是每色内部的裸服务名 platform:8001 色内唯一，互不歧义；
  • pro2 的配置就是 pro1 的直接拷贝，一行 Target 都不用改，#pro1/#pro2 down 标记成为唯一的切换开关。

教训：一个「看似要改一堆配置」的问题，往往是因为网络拓扑没分层；把隔离放到网络层，配置层就自然干净了。

7. 自举：让 CI 引擎托管它自己

这是这两天最有意思的一块（024c9d71 + run-pipeline-cicd.sh / deploy-cicd.sh）。

动机：CI 引擎（server.mjs 和一堆脚本）之前是手工 scp 到新机 ci/bin 再 systemctl restart 的——绕过 CD、无版本校验、无日志。把 scripts/ci/** 纳入流水线后，改引擎也能走「推送 → 校验 → 人工批准 → 发布」。

run-pipeline-cicd.sh 的门禁很朴素但有效：

  • syntax（硬）：对每个 .mjs 跑 node --check，每个 .sh 跑 bash -n——引擎正确性的最低门槛；
  • artifact（硬）：把 scripts/ci 整目录打包，并断言产物里含 server.mjs。

7.1 自举的死结：重启会杀掉正在部署的进程

xlagent-ci 由 systemd 管理，默认 KillMode=control-group。而 deploy-cicd.sh 是 server.mjs 的子进程，和它同一个 cgroup。于是：

systemctl restart xlagent-ci 会连同 deploy 脚本自己一起杀掉——重启之后的「健康验证 / 失败回滚」永远跑不到。

解法（写在脚本顶部注释里）：

  1. 正常模式下 deploy-cicd.sh 只做「备份 + 安装」，绝不在这条路径里重启本服务；
  2. 把「重启 + 验证 + 回滚」交给一个 systemd-run 派生的独立瞬态单元（独立 cgroup，不受本服务重启影响），靠环境变量 DEPLOY_CICD_MODE=verify 二次进入：
  1. verify 模式里再 systemctl restart + 探针 + 失败还原：
    重启后等 /healthz 起来（最多 15 次、每次 1s），200 则保留新脚本，否则 rm -rf bin && cp -a 备份 再重启。

7.3 又一个坑：脚本被常驻子进程「挂住」

deploy-orchestrator.sh 要重启一个常驻 daemon（python3 orchestrator/daemon.py）。最初的写法 ( … & ) 被 bash 优化成了直接子进程，于是本 shell 会一直 wait 这个永不退出的 daemon → 部署脚本永不返回 → server.mjs 收不到 close 事件 → 部署进度卡在 running。

修法（193d8d97）：用 setsid 起新会话，再 disown 把后台作业移出本 shell 的作业表，并把 stdout/stderr 全部重定向到日志文件，避免 daemon 持有 server.mjs 的 stdout 管道：

自举这一块，本质上是分布式系统的经典自伤问题：一个进程试图重启它所属的那个服务。所有修法（独立 cgroup / 新会话 / disown / 权威结论行）都在绕开同一个约束——重启者不能被被重启者带走。

8. orchestrator 接入：py_compile 门禁 + 常驻 daemon 重启

GPU 编排器（autodl-orchestrator）的流水线 run-pipeline-orchestrator.sh / deploy-orchestrator.sh：

  • syntax 门禁 = python3 -m py_compile orchestrator/*.py；
  • CD：备份 .py → 解包 → 就地安装 .py → 重启 daemon（pkill → setsid 起新实例）→ 探针 http://127.0.0.1:8787/health = 200 → 失败回滚。

一个关键约束：.env（密钥）和 data/（队列 db）绝不随产物覆盖——部署脚本只搬 .py 源码。这也是”部署”和”初始化”要分开的典型场景：现场数据不属于制品。

9.2 让”进行中的构建”可见

构建报告要等流水线结束才落盘，所以运行期间管理页看不到任何行。两个补丁：

写在最后

两天时间，把这套东西从「一次裸端口事故的补救」做成了一个能托管自己、能管五个仓库、一次点击带回滚锚的轻量发布系统。回头看，最有价值的不是那些脚本本身，而是三个判断：

  1. 门禁要分「硬 / 报告」——一次性全硬会把团队推到”绕过 CI”的一侧，反而更糟；
  2. 自动化的边界要保守——CI 必须自动且严格，CD 必须人工且可回滚；
  3. 自举类系统的一切复杂度都来自一个约束——重启者不能被被重启者带走。想清楚这一点，systemd-run / 新会话 / 权威结论行就都是它的自然推论了。

一点反省：这两天为了赶进度，「蓝绿色隔离」的方案改了两轮（先”颜色专属 Target”、后”每色独立网络”），说明我在动手前对网络拓扑的分层设计想得不够深。下次遇到”看起来要改一堆配置”的问题，应该先问：「是不是某一层没隔离干净？」

下一步想把 Gitee 状态回写换成别的方式补上（哪怕发飞书也行），再把这套流水线的失败用例沉淀成回归清单。
